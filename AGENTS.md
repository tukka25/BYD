# Agent Notes

## Repo Reality (not a single app)
- This repo contains multiple independent projects: `backend/` (FastAPI), `byd-web/` (Next.js), `chartist-finetune/` (the fine-tune pipeline), `web-crawler/` (Scrapy), and `langchain-archeticture/` (standalone LangGraph example).
- There IS now a top-level runner: root `Makefile` and `docker-compose.yml` drive backend + frontend + Postgres together. `make help` lists targets; `make doctor` reports what is missing. Individual projects still work standalone.

## Known-good Commands
- Whole stack: `make setup`, then `make serve-model` (terminal 1) and `make up` (terminal 2), then `make smoke` to prove it end to end.
- Frontend (`byd-web/`): `npm run dev`, `npm run lint`, `npm run build`.
- Backend (`backend/`): `docker compose up -d` from the repo root, or local API with `uvicorn app.main:app --reload --port 8000`.
- Sample data: `make sample-data` writes four seeded CSVs into `backend/uploads/` (gitignored, so regenerate after a clone).
- Web crawler (`web-crawler/`): `scrapy crawl plotly_python -s CLOSESPIDER_PAGECOUNT=10 -O plotly_examples_sample.jsonl` for a short run; omit `CLOSESPIDER_PAGECOUNT` for full crawl.

## Backend gotchas that are easy to miss
- `backend/app/main.py` creates tables on startup with `Base.metadata.create_all(...)`; there are no Alembic migrations in repo.
- `backend/.env.example` sets `UPLOAD_DIR=backend/uploads`. Because this is resolved from current working directory, launching uvicorn from `backend/` resolves to `backend/backend/uploads` (not `backend/uploads`). Set `UPLOAD_DIR` explicitly for local runs.
- Generation runs on the MLX backend by default (`LLM_BACKEND` defaults to `mlx` in `docker-compose.yml`; `make serve-model` hosts the base model plus the chartist adapter: lora-v2 since 2026-11-22, `ADAPTER := runs/adapters-mlx-v2` in the Makefile; `make serve-model ADAPTER=runs/adapters-mlx` serves lora-v1, and `make adapter` rebuilds v2 from `PEFT := cloud/artifacts/out-v2`). Ollama is the alternative backend, not the default. Generation can run long; the frontend proxy and backend both include timeout handling.
- Every model-calling role shares that one server, and so the chartist adapter: compose defaults `MLX_MODEL=default_model` and leaves `MLX_CHARTIST_BASE_URL` empty. Measured 2026-11-21 on 118 frozen questions (`chartist-finetune/data/role_measure.json`), this is what makes the planner and narrator work. Planner right: adapter 80.5%, base weights 22.9%, base with thinking off 58.5%. On base weights with thinking on, Qwen3.5 opens every reply with a "Thinking Process:" essay and never answers inside the planner's 256 tokens (all 22.9% came from the keyword fallback); the narrator's 128-token cut leaves essay fragments as titles. Narrator usable titles: adapter 100%, base 0%, base with thinking off 100%. So do not move the planner to base weights; a title writer can run on base weights only with thinking off (`enable_thinking=False`, which the mlx_lm server accepts per request as `chat_template_kwargs`). lora-v2 (`data/role_measure_v2.json`): planner 77.1% (9 lost, 5 gained against v1, p=0.42; its new chart types leak into the labels, "cumulative ... building up" now reads as waterfall), narrator 100%.
- `CHARTIST_CHART_TYPE_HINT` (`off` | `inline` | `directive`, default `off`) sends the planner's chart type to the chartist. It is sent only when the plan's `chart_type_source` is `llm` or `keywords` — never `default`, the bare "bar" used when nothing decided — and never when the question already names its chart, which is every architect-written dashboard question. The text is `chart_type_hint()` in `chartist_contract.py`, re-exported to `chartist-finetune/contract.py` so training data and the live prompt cannot drift. Measured on lora-v1 (`chartist-finetune/data/ab_planner_hint.json`, 118 frozen questions): with an oracle chart type, right kind of chart 68.6% -> 81.4% but renders 91.5% -> 81.4% (p=0.017 each; worst where one label, "treemap", covers four chart types). With the real planner's 80.5% the shape gain vanishes and the render loss stays. Keep it `off`: lora-v2 was not trained on it either (0 "Chart type:" rows in `data/mlx_v2_capped/train.jsonl`; its plan form carries the chart kind in a `Chart plan:` block instead).
- `architect.profile_frame` (now only behind `DASHBOARD_PLANNER=rules`) only tries to parse a text column as a date when its NAME matches `_TIME_NAME`: across the 180 fixture tables it found no date in 57 (32%), and "churn by country" never finds `cntry_cd`. Its replacement, `agents/profiler.py`, reads values only and agrees with the generator's own column roles on all 1,382 fixture columns (180/180 dates). Never add name rules back; the model reads the examples the profiler prints.
- `DataDetective.detect_source(plan=...)` accepts the planner's plan and never reads it.
- `CHARTIST_MAX_TOKENS` (1024, `chartist_contract.py`) is the one generation cap for production, `evaluate.py` and the A/B harness. Evals used to stop at 800; lora-v1's recorded numbers were measured at 800.
- `SECRET_KEY` and `ENCRYPTION_KEY` are not set in the root `.env`, so compose falls back to defaults that are committed in this repo: tokens can be forged and saved database-connection passwords decrypted by anyone with the repo. `make secrets` generates real ones. Rotating `ENCRYPTION_KEY` makes already-saved connection passwords unreadable, so re-enter each connection afterwards.

## Frontend integration details
- Frontend backend URL resolution in `byd-web/app/api/dashboard/generate/route.ts`: `BACKEND_API_URL` -> `NEXT_PUBLIC_API_BASE_URL` -> `http://127.0.0.1:8000`.
- General API helpers use `NEXT_PUBLIC_API_BASE_URL` with default `http://localhost:8000` in `byd-web/lib/backend.ts`.
- Auth/session are localStorage-based (`promptdash_session_user`, `promptdash_access_token`) in `byd-web/lib/auth.ts`; no cookie/session middleware.
- Routes after the UI rebuild: `/` reports home, `/reports/new`, `/reports/[id]` (the canvas), `/data` (sources), `/login`. The old `/dashboard/new`, `/dashboard/new-canvas` and `/settings/data-sources` are now redirects, not pages.
- Canvas blocks are backend-owned (`backend/app/api/v1/endpoints/blocks.py`, table `report_blocks`), not localStorage. `POST /blocks/generate` runs the agent workflow; `PUT /blocks/layout` persists drag/resize.
- An all-`indicator` Plotly figure is stored as a `metric` block at tile size and titled with the label the model wrote. That is the KPI stat-card path; there is no separate "make me a KPI" endpoint.
- `byd-web/DESIGN.md` carries the design system (tokens, components, the Plotly re-theme contract). Read it before touching UI.
- The comparison builds WHOLE dashboards now: both sides get the same architect plan (same sections, same geometry) and each renders as a 12-column dashboard. The opening text block is composed from the data profile, not a model, so it is identical on both sides and is shown once above them.
- A run is cached in `sessionStorage` (`promptdash_last_comparison`), because a four-minute run that costs real money should survive a reload. Still not persisted to the database: a comparison is an experiment, not a report.
- Real-data demo in Postgres: `spotify_songs` (32,833 rows, TidyTuesday 2020-01-21, from the Spotify API) loaded with `to_sql` into the app's own `promptdash` database, reachable through the "Local Postgres" connection. Re-create with: `curl -sS -o backend/uploads/spotify_songs.csv https://raw.githubusercontent.com/rfordatascience/tidytuesday/main/data/2020/2020-01-21/spotify_songs.csv` then `pd.read_csv(...).to_sql("spotify_songs", engine)` inside the api container.
- Measured there with the brief "track popularity and energy by genre": local 5/5 from its own code, Opus 3/5 from its own code plus 2 cells drawn by the deterministic fallback, $0.242. (An earlier scoreboard counted the fallback cells as Opus wins and read "5/5 vs 5/5"; commit 7ad7a30 fixed it.) The local model's weakness there was aggregation — it drew 32,833 raw rows as a line — which the architect's wording now fixes.
- `Compare models` (`/compare`, `backend/app/api/v1/endpoints/comparison.py`) runs the same question on the local chartist and on Claude Opus 5.5. Fairness is by REUSE, not by copying: one sampled DataFrame, one schema block, one planner call, the same `ChartistAgent` class (same prompt from `chartist_contract.py`, same reply reading, same contract validation, same repair turn) and the same `SafeExecutor` and repair loop (`workflow.run_on_frame`). A cell records `repairs`, how many times the model had to fix its code; API tokens are summed across those calls. `ChartistAgent(llm=None, generator=...)` swaps only the text-generation step.
- `backend/app/services/claude_chartist.py` is the only Anthropic SDK code; `llm.py` stays OpenAI-shaped for the MLX server and is untouched. Opus notes: thinking cannot be disabled, `temperature` is rejected, `output_config={"effort": ...}` is the only dial (`CLAUDE_EFFORT`, default medium), and server-side refusal fallbacks are deliberately OFF — a silent model switch would invalidate the comparison, so a refusal is surfaced as a failed cell.
- Comparison results are NOT persisted. It is an experiment, not a report. Cost is shown on screen from real `usage` tokens at published rates; a 4-question run measured $0.158.
- `backend/uploads/gapminder.csv` is a public dataset (plotly/datasets); `backend/uploads/` is gitignored, so re-fetch after a clone: `curl -sS -o backend/uploads/gapminder.csv https://raw.githubusercontent.com/plotly/datasets/master/gapminder_with_codes.csv`. Measured there: local 2/4 rendered vs Opus 4/4; both local failures were indicator/KPI traces, which the fine-tune evaluation already lists as a weak bucket.
- Four agents now: planner (chart type), detective (which source), chartist (the fine-tuned one), narrator (`agents/narrator.py`, writes the block title). The narrator never fails a request — it falls back to the question, tidied.
- The architect (not the planner) STATES the aggregation in the question it writes, because the chartist cannot infer it. Measured: "X over Y as a line chart" -> no groupby, 32,833 points; "Average X by year of Y as a line chart" -> groupby, 63 points. Same model, same data; the wording was the whole gap against Opus. `_aggregation()` picks Average for rate-like measures (pct, rate, score, popularity, tempo...) and Total otherwise — summing a score is a number with no meaning; `_grain()` picks year/month/day from the measured span.
- Demo connection: "Spotify tracks (Postgres)" points at a SEPARATE `spotify` database (table `tracks`) so the picker shows one real table instead of the app's own. Create it with `CREATE DATABASE spotify` then `to_sql("tracks", ...)` from the api container.
- Dashboards are planned by AI, checked by code (`agents/dashboard_flow.py`, default `DASHBOARD_PLANNER=ai`): the profiler describes every source (up to 6 tables) from a 2,000-row sample, the analyst proposes 4-7 directions, the planner writes every chart plan in ONE call (`chart`, `table`, `x`, `y`, `group`, `agg`, `grain`, `sort`, `top_n`, `title`), `planning_contract.check_*` tests every column against the real tables and sends failures back in plain words (at most 3 tries, best attempt kept), `layout.lay_out` places by chart kind, and the chartist draws each plan via `render_spec` + `workflow.run_chart_code`. The architect's old reason to exist (an SLM invents columns) is handled by the checks, not by banning the model from planning. Analyst and planner run with thinking off (`llm.py` `_NO_THINKING`).
- A bar chart may put a TEXT column (track names, artists) on x only with `top_n` 1-30 (`planning_contract.MAX_TOP_N`). Before 2026-11-22 it was refused outright, so "the most listened songs" on the Spotify table failed the check on all 3 planner tries and the dashboard shipped without the two charts the user asked for. The planner's prompt text was left unchanged on purpose: lora-v2 was trained on it.
- The 2,000-row sample the planner profiles is drawn across the whole table (`architect.spread_sample`: seeded, rows kept in order); files are read whole to draw from. It used to be the first 2,000 rows, and the Spotify table, stored sorted by genre, showed the planner 2 of its 6 genres and 35 of its 449 playlists. The comparison's database path uses the same sampler.
- Gotcha that cost real time: current pandas gives string columns a `str` dtype, NOT `object`. `series.dtype == object` silently classified every label column as unusable. Use `pd.api.types.is_string_dtype`. Also, never flag a float as an identifier by uniqueness — a continuous measure is naturally almost all-unique.
- The dashboard build takes an optional `brief` ("churn by region"). It does not rewrite the section order — it reorders which measures and groupings lead, by camelCase-aware token overlap with light stemming, so `churn` finds `churnedSeats`. Deterministic on purpose: the answer has to be a real column name and this cannot return one that is not.
- Number formatting is a RENDER-layer job in `byd-web/components/plot.tsx`, applied to every figure from every model: separators on KPI numbers, value labels above bars (<=12 bars), currency on the money axis. Currency is read from field/axis names (`mrrUsd` -> `$`); `NEXT_PUBLIC_DEFAULT_CURRENCY` covers columns that name none — set in the root `.env` for docker compose AND in `byd-web/.env.local` for `npm run dev` on the host (Next reads its own project dir, not the repo root). Both are gitignored, so it is per-machine; a NEXT_PUBLIC_ var is read at server start, so restart the dev server after changing it. Never invent a currency for an unlabelled column.
- An invalid or SI `valueformat` from the model is overridden; a valid deliberate one is kept. `D3_FORMAT` exists because a colour (`#1f77b4`) once landed in that field and Plotly ignored it silently.
- NO HARDCODED CHARTS, the user's standing rule (2026-11-23). Every chart is the model's own code. When it breaks the contract or fails to run, `workflow.run_on_frame` sends the problem back to the model (`CHARTIST_REPAIR_TEMPLATE`: its code as its own answer, then "That code did not work: ..."; contract breaks in plain words from `chartist_contract.problems_with`), at most `MAX_REPAIRS` = 2 times, then the chart is reported as failed with the reason: a skipped dashboard block, an error for a single chart, a failed comparison cell. Single charts, dashboard charts and both comparison engines share that loop. Removed with it: the template chart `chartist._fallback_plotly_code` (in the app since 2026-03-19; it picked columns by name and plotted every row, so on the 32,833-row Spotify table it drew one bar per row of `track_popularity` under the planned title "Average Danceability of Tracks", 868 kB, 3.5 s to draw and 4.4 s per resize), the property rename/drop driven by Plotly's error message, the `valueprefix`->`prefix` rename list, and the appended `print(fig.to_json())`. The chartist only reads the code out of the reply (fences, think prefix, curly quotes, leading prose). A model that cannot be reached raises `ChartistUnavailable` and is reported, never replaced. `report_blocks.used_fallback` stays only to label blocks saved before the change. First live miss after it: "show it in text card" put text into an indicator's `mode` three times and was reported as failed.
- `POST /dashboard/{id}/blocks/dashboard` streams SSE (`status`, `plan`, `step`, `block`, `skipped`, `error`, `done`). `status` covers the planning calls before a plan exists, including one per retry ("Planning the charts, try 2 of 3"), and each failed try is logged as `[planning] planner try 1 of 3: ... problem(s): ...` (a retry is another 25-40 s call; on the Spotify table five calls behind one label read as a stuck build); `error` ends a build whose plan failed the checks (the client throws it like an HTTP error). One failed block is `skipped`, not a failed build. Client parser is `generateDashboard` in `byd-web/lib/blocks.ts` (POST, so EventSource is out). Smoke on lora-v1 (`backend/scripts/smoke_dashboard_flow.py`, s0016, "watch time by country"): 7 planned, 7 rendered (3 by the backup chart), 204 s; the planner call alone took 100 s. On lora-v2: 7 of 7 by the model, 0 by the backup, plans passed the checks first try, 125 s.
- Planner tools (`agents/data_tools.py`, `agents/discovery.py`, `PLANNER_TOOLS`): an explorer call asks the model to check up to 3 facts (find_columns, inspect_column, relationship, preview; results capped at 1,200 characters, 20 items, with truncation markers), and the analyst and planner get only a facts note of at most 800 characters; final plans are also checked on the real data (more than 50 bars, 12 slices or 1,000 line points goes back to the planner). Measured on the first 40 of the frozen 120 planning requests (`chartist-finetune/measure_planning_tools.py`, `data/v2/planning_tools_*`). Tools off: analyst usable 100%, planner first try 87.5%, total failure 0%, charts dropped 0.025 per dashboard (problem lines 0.05 per dashboard), median 65.85 s. Tools on: analyst usable 100% (1 row needed an analyst retry, 2.5%; off 0%), planner first try 87.5%, total failure 0%, charts dropped 0 per dashboard (problem lines 0), median 81.25 s. The two first-try definitions agree in both arms because no asked dashboard produced zero charts. Paired on the same 40 ids: first try 2 better on, 2 better off (exact sign test p=1.0); charts dropped 1 fewer on, 0 fewer off (p=1.0); median paired seconds delta +13.5. Default on (`PLANNER_TOOLS` in `backend/app/core/config.py`) because all four no-harm checks pass (first try not lower, dropped not higher, analyst usable not lower, median rise 15.4 s under the 30 s line). This is a no-harm gate, not evidence of gain: first try and analyst usable tie, and the one dropped chart is one dashboard (p=1.0). The tool step costs about 15 s median per dashboard and 3 tool calls. Caveats: 40 rows only; the tools-off arm ran at `29d29f6` and the tools-on arm at `2a97d95`. The harness imports every planning module at start, so each arm used the code at its start commit; `2a97d95` changed only `backend/app/services/db_sources.py` (and its test) from `29d29f6`, and later planning commits (for example `00f4d61`) are not in the tools-on rows. Only the tools-on arm runs the data checks (`ToolBox.validate_spec`), so its first try and dropped charts face stricter checks. The tools-on arm ran while other work was using the machine, so part of the 15.4 s gap may be load. Report memory (`agents/report_memory.py`, table `report_requests`) gives the analyst the report's charts and the last 5 requests.
- A line or area plan with `agg` none whose x repeats within one line (per `group`) goes back to the planner in words: "x 'hourOfDay' has 24 values over 168 rows (each appears 7 times), so one line would run back and forth: set agg (mean for rates, sum for totals) or a group". The check is `data_tools.repeated_x`, reached through `chart_shape`, which `ToolBox.validate_spec` calls, so it runs with the other data checks. It was found from "Bounce Rate by Hour": 168 weekday × hour rows drawn as one line over the hour.
- Every placed chart plan is logged with all its fields: `[dashboard] chart plan 2 of 7: {"chart": "line", ..., "agg": "none", ...}`. A bad chart can then be traced to its plan or to the code drawn from it.
- Database sources are real: `backend/app/services/db_sources.py` holds the whole path. PostgreSQL (psycopg2) and MySQL/MariaDB (pymysql) only — those are the two whose drivers install cleanly and spell `connect_timeout` the same way. `GET /data-sources/database-kinds` reports which drivers the server actually has.
- A connection is probed before it is stored (`POST /data-sources/db-connection` connects first and 400s with the driver's own error). `POST /data-sources/db-connection/test` is the same probe without saving.
- The agent sees TABLES, not connections: `candidates_for()` turns each table into a candidate `{id: "<source id>:<table>", type: "db", columns}`, the detective ranks it beside files, and the executor loads it with `load_table_by_id` into the same `df`. Nothing downstream knows the difference. Table names are never interpolated into SQL — tables are checked against the live list then reflected.
- Declared foreign keys become joined tables (`db_sources.Link`, `candidates_for`): `orders+customers` is a left join keeping one row per order, with the customer's columns named `customers.region`; at most 6 per connection, one hop, child to parent, never guessed from names. Two keys between the same two tables are named by key (`orders+customers_by_billing_customer_id`), so the planner can tell them apart. The analyst and planner get one line per join, at most 4 (`agents/links.py`). Demo: `backend/scripts/make_relational_demo.py` builds a `shop` database with customers, products and orders. Live check (2026-11-23, lora-v2, `PLANNER_TOOLS=on`, brief "revenue by customer region and product category"): 7 charts, all by the model, 6 on joined tables (3 `orders+customers`, 3 `orders+products`); the KPI and two charts checked equal SQL over the joins to the cent. The analyst's first try put `products.category` on `orders+customers` and the checks sent it back. A joined table has one parent, so a chart crossing two parents (region by category) cannot be planned yet.
- A declared key into another schema (Postgres) or another database (MySQL) is not joined: `db_sources.links_on` skips a `referred_schema` other than the connection's default. The parent is reflected by its bare name, so a same-named table here would be joined instead, with wrong numbers and no error.
- `MAX_ROWS = 500_000`: a chart reads the whole table so totals are real, and above that it refuses with the row count rather than silently charting a LIMIT.
- `_user_sources` in `blocks.py` now scopes generation to a report's own `data_source_ids` when it has any. Before this the picker recorded a choice and generation ignored it.
- Note blocks store HTML, not plain text. `byd-web/lib/rich-text.ts` is the trust boundary: it sanitises on commit AND on render (allowlist of 14 tags, no attributes except a validated href). Never render `text_body` without it. Legacy plain-text bodies still render — `toHtml` handles both.
- Plotly is bundled (`plotly.js-dist-min`, lazily imported in `components/plot.tsx`), never the CDN script — the CDN broke the local-only claim and pinned an old Plotly.
- Gotcha: `react-grid-layout` positions items with `transform`. Any CSS animation that touches `transform` must sit on an element INSIDE the grid item; on the item itself, `animation-fill-mode: both` makes the keyframes' final `transform: none` beat the inline grid transform and all blocks pile up top-left. `globals.css` keeps a `.react-grid-item.block-settle { animation: none }` guard.
- `react-grid-layout` v2's classic API lives at `react-grid-layout/legacy`; the root export is the new rewrite and has a different surface.
- Chart kinds: the "/" menu and the chart kinds panel read a fixed list in the frontend, `CHART_KINDS` in `byd-web/lib/chart-kinds.ts`; nothing fetches it. `backend/tests/test_chart_kinds_frontend.py` reads that file as text and fails unless its ids and labels equal `planning_contract.CHART_KINDS` and the labels in `agents/chart_kinds.py` (`KIND_INFO`), so the UI can only offer kinds the planner accepts; change both sides together. A pick travels from the UI to the API as `chart_kind` (one chart) or `chart_kinds` (a brief, up to 4), checked at the API (422 otherwise), never as text typed into the prompt; inside the backend the analyst and planner are told the kind in words. One chart in a picked kind goes through `agents/kind_request.py`: the detective picks the table, the planner writes one plan that must be that kind (a joined table comes with its join line, as on a dashboard), and the chartist reads it as the `Chart plan:` block lora-v2 was trained on. The `[blocks] generate` log line names the pick (`chart_kind=treemap`, or `-`). The panel's thumbnails are figures the model drew (`backend/scripts/make_chart_kind_examples.py` -> `byd-web/public/chart-kinds/examples.json`); regenerate after an adapter change, and on the compose stack run `make up` so the web image is rebuilt with it (compose does not mount `public/`). A file that does not load shows in the panel as "Could not load the examples (HTTP <status>)", never as "No example yet". Frontend logic tests run with `npm test` (Node's own runner, no framework).
- A kind picked for a dashboard is now told to the planner up front, in the analyst's words: `Include these chart kinds: Pie chart.` is appended to its message by `chart_kinds.include_kinds`. Before, it heard of the pick only in a retry message.
- The planner's best try is now the one with the most picked kinds, then the most charts (`planning.run_checked(rank=...)`). Before, a try with 7 charts and no pie beat one with 6 charts including a valid pie. That was the final review's reproduction.
- A kind still missing after the last try is named in the SSE `plan` event as `missing_kinds` and logged with the plan. It is not a `skipped` event, because that event counts as a finished block.
- The canvas shows `missing_kinds` as one muted line above the blocks, "Could not plan a pie chart for this data." (`byd-web/lib/kind-notice.ts`, import-free so `npm test` loads it). It shows from the plan until the next build.
- Kind requests on wide tables, live check 2026-11-23 (lora-v2, `backend/scripts/check_kind_columns.py`). `/box` "energy by genre" on Spotify `tracks` (23 columns, `energy` not among the 12 the direction lists) planned x=playlist_genre y=energy, rendered yes. `/box` "minutes by customer segment" on the shop demo's `visits+customers` (18 columns, no parent column listed) planned x=customers.segment y=minutes, rendered yes. The planner found both columns in the full profile, so the direction still lists the first 12 profiled columns.
- Example run, 2026-11-23 (lora-v2): `make_chart_kind_examples.py` drew 13 of 13 kinds in its one run, each the trace type it names (176,797 bytes).
- Browser check, 2026-11-23 (lora-v2, `PLANNER_TOOLS=on`, shop demo): `/tre` + "revenue by product category" gave a treemap on `orders+products` whose values equal SQL (the api logged the block created 16.6 s after the request).
- Same check: a dashboard brief with `/pie` included a pie among 7 charts, but the analyst needed 3 tries on it because it kept crossing the two joined tables (region and category), the one-parent join limit again.
- The panel's pie thumbnail spills its labels past the 96x64 box.
- Gotcha that cost real time: after `make up` rebuilt the web image, every page answered 500 with Turbopack's `next/font/google queries have exactly one entry` (`Can't resolve '@vercel/turbopack-next/internal/font/google/font'`) for JetBrains Mono; the fresh container's first font fetch probably cached a `fonts.gstatic.com/l/font?kit=...&skey=...` URL that Turbopack cannot parse (not reproducible from the host, where Google served the usual `/s/` URLs). `layout.tsx` was not the cause. Fix: `docker exec promptdash-web rm -rf /app/.next/dev` then `docker compose restart web`.

## Fine-tune facts that change decisions (`chartist-finetune/`)
- lora-v1's recorded 91.3% render / 81.0% right shape (`cloud/eval_report.json`) is a lower bound. 16 of its 25 recorded failures are a `pyarrow` import crash in the eval pod (`pyarrow._fs._init_ca_paths` -> `ssl.py`), all in the treemap/funnel/waterfall bucket — an environment failure, not a model error. Re-measure locally before spending money on that bucket. Re-scored locally with a working pyarrow (`data/ab_planner_hint.json`), lora-v1 renders 86% of that bucket.
- The 7.7% base figure is with thinking ON. Against the base model with thinking OFF, on the same 118 questions: renders 62.7% vs lora-v1 91.5%, right kind of chart 23.7% vs 68.6% (lora-v1 better on 54, worse on 1). Most of "7.7% -> 91.3%" is the reasoning essay, not the fine-tune; what the fine-tune bought is choosing the right chart, and that knowledge also lifts the planner (58.5% -> 80.5%).
- lora-v2 (2026-11-21, `cloud/README.md`): 97.3% render / 87.0% right shape on the pod in bf16. On the Mac, 4-bit, same harness (`data/eval_report_local_v{1,2}.json`): v1 89.3% / 76.3%, v2 94.3% / 82.3%; render paired 26 vs 11 discordant, p=0.020. 4-bit costs v2 3 points of render against bf16. v2 went the other way on the Mac on gauge/indicator (16 -> 13 of 17) and box (22 -> 20 of 23); on the pod gauge went up (82.4% -> 88.2%) and box lost one (23 -> 22).

Funnel and sunburst have zero examples there; lora-v2 added 535 (`data/v2/new_targets.jsonl`: KPI 150, waterfall 143, funnel 123, sunburst 119). "34 trace types" elsewhere counts the rewritten docs rows.
- Target yield was 98.8% (1,897 kept of 1,920 attempted). `questions.jsonl` also holds 960 test-split questions that were never given targets, so comparing question counts with target counts overstates rejection.
- Area, line, time series and scatter targets all build `scatter` traces, so trace type cannot separate them; `chart_types.is_area_figure` breaks the tie in scoring. That is why area renders at 100% but is the right chart far less often.
- The production missing-field note ("Not available in this data, do not use: ...") appears in 0 of 1,929 training rows (and 0 of lora-v2's 7,321), so it is as untested as the chart-type hint.

## Verification shortcuts
- `make smoke` is the fastest real check: health, register, login, that `/generate` refuses an anonymous call, then a real chart with real data points. Nothing but the model ever draws a chart, so a green result means the model's own code drew it (after at most two fixes).
- `make doctor` reports docker, api, model server, sample CSVs, adapter and base model in one line each.
- `GET /health` reports the active backend, model, upload dir and whether the committed placeholder secrets are in use.
- There is no established Python test suite config (`pytest.ini`/`pyproject.toml` absent). `backend/test_agent.py` is a manual workflow script, not an isolated unit test.
- See `docs/slm-harness-evaluation.md` for the prompt/harness review and the measured before/after numbers.
- `chartist-finetune/measure_planning.py` scores the AI dashboard flow end to end on the frozen 120 planning requests (`data/v2/planning_testset.jsonl`, sha256 `8af1473a`; `export_v2.py` refuses any training row from their 60 schemas). It draws only the FIRST 3 plans of each dashboard (`--max-charts-per-dashboard 3`). lora-v1 (`data/v2/planning_eval_lora-v1.json`): analyst 98.3% usable, planner 100%, 54% of dashboards needed a retry (the slow planner call), 86.4% of drawn charts render, 84.9% as the planned kind; heatmap (12/38 fail), KPI (10/50) and line (11/78) were the weak kinds. lora-v2 (`planning_eval_lora-v2.json`): 99.2%, 100%, 12.5% retries, 98.9% render, 98.9% planned kind. Read v2's with its mix: it opens with KPIs far more often (112 of 357 drawn vs 50 of 352) and drew only 13 heatmaps, so its drawn mix is easier; per kind it still wins (KPI 112/112, line 106/108, heatmap 13/13). Compare any new adapter on this set, not on ad-hoc dashboards.
